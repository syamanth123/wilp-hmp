## 1. Due dates for every stage (F4) — the base for everything else

- Each request gets a **due date per stage**, shown on the request page, in "My work", the dashboard, the Library
  and the calendar:

  | Stage         | Who          | Default due (days **before the semester starts**) |
  | ------------- | ------------ | ------------------------------------------------- |
  | Allocation    | HOG, then PC | 35                                                |
  | Faculty draft | Faculty      | 21                                                |
  | SME review    | SME          | 17                                                |
  | PC review     | PC           | 14                                                |
  | HOG final     | HOG          | 10                                                |
  | Publish       | IC           | 7                                                 |

- **Late starts get fair time:** a stage's due date is the later of the date above and "the day the stage began +
  its SLA" (today's SLA hours, plus a new SME one). So a request created a week before the semester isn't overdue
  on day one. A handout **sent back** gets a fresh due date by the same rule.
- **Editable per request** by the IC and the request's HOG, with a reason (audit-logged). An edited date is kept
  when the stage restarts.
- **Overdue is measured against the due date**, not `updatedAt`. SLA widgets, reminders, the Library and the
  dashboard all use it, so editing a draft no longer resets the clock.
- **Worked out, not stored:** the dates come from the rule each time they are shown; only a date someone changed
  is stored. So existing requests have their dates from the moment of the release, and changing an offset in
  Admin → Workflow moves every date that wasn't changed by hand. A stage's start comes from a new
  `statusChangedAt`, filled for existing requests from their history at the release.
- **Admin → Workflow** gains the six offsets and the SME SLA.

## 2. Reminders and escalation (E) — person → HOG → IC

Daily at **09:00 IST**:

| When                         | Who gets it                                                             |
| ---------------------------- | ----------------------------------------------------------------------- |
| 2 days before the due date   | the person holding it ("due soon", as today)                            |
| on the due date / overdue    | the person holding it                                                   |
| overdue by **N** days (3)    | + **the request's HOG** ("Dr A's draft for SS ZG653 is 3 days overdue") |
| overdue by **2N** days (6)   | + **the Instruction Cell**                                              |
| HOG's own stage overdue by N | + the Instruction Cell (no HOG above them)                              |

- Each step is sent **once** per stage and due date. Changing the due date starts again.
- A person who is away (§4): their back-up gets it too.
- **Admin → Workflow → Escalation**: on/off, N days, and **"What tomorrow's run would send"** (a list, nothing
  sent) — see H26.

## 3. "My work" (E) — on every home page

- At the top of every role's home: **the items that need _my_ action, sorted by due date**, each with what to do
  and the due date ("Review SS ZG653 Software Testing — due 12 Dec · 2 days left" / "3 days overdue" in red).
  - Faculty: accept allocation, write / revise the draft.
  - SME: reviews. PC: allocations to confirm, reviews. HOG: allocations, final approvals.
  - IC: approved, waiting to publish; auto-publish problems (§10); escalations sent to the IC; "what's missing"
    count.
  - Back-up: the away person's items, marked "for Dr X (away until 20 Nov)".
- A person with two roles sees one list, each item tagged with its role.
- Empty: "Nothing needs you right now."

## 4. Away and back-up

- **My settings → Away**: "Away from … until …, back-up: \<a colleague with the same role\>". The IC and Admin can
  set it for someone (e.g. sudden leave).
- **While away**, the back-up **sees** the away person's requests, **gets** their notices and reminders, and **can
  act** for them. Each action is recorded as "Dr Y for Dr X". The away person keeps the requests: nothing is
  reassigned, so nothing has to be moved back. It ends on its own after the last day.
- **Pickers** show "away until 20 Nov · back-up Dr Y" next to the name. New requests still name the department's
  HOG; the back-up handles them meanwhile.
- **For HOG, PC, SME and IC.** Faculty can mark themselves away (the pickers show it), but a back-up doesn't write
  their draft: the HOG changes the faculty if needed (H18).
- The back-up must be active and have the same role. For a HOG, that is usually another department's HOG (one HOG
  per department), so the department scope widens for the back-up during the away dates only.

## 5. Department dashboard (E)

- **IC / Admin:** Departments → **Dashboard**: one row per department × _not started_ (Dibba courses without a
  request), _in progress_, _overdue_, _approved_, _published_, for the chosen semester. Every number opens the
  Library with that filter.
- **Workload table** under it: per person — role, open handouts, due this week, overdue, away. Sorted by overdue.
- **HOG:** the same page for their own department, from the HOG menu.

## 6. Creating requests

1. **Semester kick-off wizard (F3, plus §E bulk assign)** — IC → Requests → **Kick off a semester**:
   1. Pick the semester (the last one used is remembered, F12).
   2. All Course Dibba courses for it **without a request**, grouped by department, ticked by default. Problems are
      shown and can't be ticked: department unknown, department has no HOG, programme or semester missing in HMP
      (each with a _Fix_ link).
   3. **Preview:** per course: HOG, the six due dates, starting content ("Last year's handout: Sem-I 2025-26" /
      "BITS archive" / "Blank"), duplicates skipped.
   4. **Create N requests**. Each goes to its department's HOG, as bulk upload does today; same engine.
2. **Dibba instructor suggested (F1):** on Allocate, at the top of the faculty picker: "Suggested: **Dr X** —
   Course Dibba instructor, Sem-I 2026-27" (the lead first), with **Use**.
3. **Last semester's team (F2):** "Same team as **Sem-II 2025-26**: Dr A (faculty), Dr B (SME), Dr C (PC) — **Use
   this team**". It comes from the most recent earlier request for the same course in the department. People who
   are inactive or away are marked; the HOG still confirms.
4. **Duplicate guard (F5):** single creation (New request and the Library's _Create request_) uses bulk upload's
   rule: if the course already has a request this semester (anything but Rejected / Archived), it stops and links
   to it ("HMP-2026-0012 already exists for SS ZG653, Sem-I 2026-27 — open it").

## 7. Emails and notices

1. **Daily digest option (F6):** **My settings → Email**: _Each notice at once_ (default) or _One email a day at
   09:00_. Urgent items are always sent at once: sent back for changes, overdue / escalation, @mentions. In-HMP
   notices are unchanged. The digest groups _Action needed_ / _For information_, with a link per item. (The
   detailed layout comes with §G in v1.4.3.)
2. **Weekly summary (F7):** Monday 09:00. HOG: their department — started, in progress, overdue (with names),
   approved, published this week. IC: the same per department. Each person can switch it off in My settings.
3. **Deep links (F8):**
   - the full link survives sign-in (password and BITS), `?…` included;
   - the password sign-in only follows links inside HMP (the BITS sign-in already checks);
   - SME links open the handout itself;
   - a person with two roles gets the page for the role the notice is about.
4. **@mentions and replies (F10):** type `@` in a comment → the people on this request (HOG, PC, faculty, SME,
   IC). The person mentioned gets a notice in HMP **and an email**. **Reply** on a comment notifies everyone in that
   thread. The SME now gets comment notices too.
5. **Calendar (F9):** My settings → **Add my HMP deadlines to my calendar**: a private link for Outlook / Google
   Calendar that updates by itself. It holds only course code, title, stage and due date — no handout content. It
   can be replaced with a new link at any time (the old one stops). See H21.

## 8. People

1. **Handover on deactivation (F13):**
   - Edit person gets a clear **Deactivate (leaving)** button. It lists all their open work and hands it over in
     one step (one person for all, or one per item), then ends their session.
   - The old Users-page _Deactivate_ link now goes through this; today it skips the check.
   - Deactivating someone also removes them as anyone's back-up (the away person is told).
2. **Undo a role / department change within 24 hours (§B2):**
   - On Edit person, after a change: "Changed by Asha on 12 Nov 10:40 — **Undo** (until 13 Nov 10:40)".
   - Undo puts back roles, department, faculty type and active. Audit-logged; the person's menu updates on their
     next page.
   - Work handed over in that change **stays** with the new person (the page lists it, with links to change it
     back per request).
   - Only the latest change can be undone, and only by someone allowed to make it (an IC can't undo an Admin's
     change to the Admin role).
   - People-upload changes can be undone per person; the upload starts recording "before" for this.

## 10. Auto-publish (F11) — off by default

- **IC → Earlier runs → Settings:** "Publish to Taxila automatically after final approval" — **Off** until the IC
  or Admin switches it on. Only shown when Taxila is set up on the server.
- **When on:**
  - right after the HOG's final approval, the worker runs **Check in Taxila**;
  - if the check passes, it **publishes**, with the same rules as today: one `Course Handout.pdf`, read-back
    confirm, and the faculty is told.
- **Anything else stays Approved and goes to the IC's "My work"**, with the reason and the IC told:
  - course not found;
  - several courses match;
  - no Course Handout item;
  - other files in the item;
  - not confirmed;
  - a Summer semester, whose Taxila code can't be worked out.
- No automatic retries: the IC fixes the problem and presses Check / Publish as today.
- Each automatic publish shows in **Earlier runs** as an "automatic" run, with the same log.

## 11. How the daily and weekly runs happen (H15)

- **Inside `hmp-worker`**, which already runs on the server, as BullMQ scheduled jobs:
  - daily 09:00 IST: reminders + escalation, then digests;
  - Monday 09:00: weekly summary.
- **No server step**, and they survive every release.
- Each run is recorded once per day / week (`ScheduledRun`), so it **never sends twice**, even if the old reminders
  URL is also called by a timer, or the worker restarts.
- Admin → Notifications shows the last runs (time, sent, failed) and keeps **Run now**.
- **If `hmp-worker` is down**, nothing is sent that day. The next run sends what is due then, and Admin → Queues
  already shows the worker's heartbeat.

## I. As built (v1.4.2)

- **Due dates:**
  - `lib/deadlines.ts` works them out; only hand-changed dates are stored (`RequestDeadline`).
  - `HandoutRequest.statusChangedAt` is set by `transition()`.
  - Used by My work, the Library, the picker load, the SLA widgets, the dashboard, reminders and calendars.
  - `components/stage-deadlines.tsx` is on every request page. Finished steps show when they were done.
- **Daily / weekly runs:**
  - A third BullMQ queue, `schedule`, in `hmp-worker`. `registerSchedules` sets daily 09:00 and Monday 09:00
    India time, upserted by id.
  - `lib/daily-run.ts` claims each run once (`ScheduledRun`).
  - `/api/cron/reminders` now runs the same daily run, once per day.
  - Admin → Notifications → Run now runs it on demand. Each step is still sent once (`EscalationStep`).
- **Escalation:** `lib/escalation.ts` (`levelReached`, `planRun`).
  - Levels: 0 due soon; 1 overdue; 2 + HOG (for a HOG's own step, + IC); 3 + IC.
  - A request first seen at a high level gets only that level.
- **Digest:**
  - For people on the daily digest, `deliver()` keeps emails that aren't urgent PENDING (`meta.digest`).
  - `sendDigests` sends one email per person.
  - Urgent: sent back / rejected events, reminders, @mentions.
- **Away / back-up:**
  - Code: `lib/away.ts`, `lib/away-save.ts` (the back-up is told) and `lib/backup-access.ts`.
  - The back-up reaches the requests through `requestVisibleTo` (detail pages and every HOG / PC action), the
    named-PC and assigned-SME checks, My work and notices (`withBackups`).

  - Lists and bulk tools keep the person's own scope; the back-up works from My work.
