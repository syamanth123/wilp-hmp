## 1. One layout for every email (built — screenshots 01–11)

Every email has the same parts, in this order. A part with nothing to say is left out, so there are no empty
boxes or "undefined".

1. **Subject:** `[HMP]`, what happened, and the course:
   - `[HMP] Action needed: review SE ZG503 Full Stack Application Development (Sem-I 2025-26) — due 16 Nov 2026`
   - `[HMP] Changes needed: …` / `[HMP] Published: …` / `[HMP] Overdue: …`
2. **One-line summary** in plain words: "PC Member sent the handout for SE ZG503 … back to you for changes."
3. **What you need to do**, or **"No action needed — for your information"**. When there is something to do, it
   ends with the due date and the days left or overdue: "By 06 Nov 2026 · Faculty draft · 5 days overdue". The
   due line is red when overdue and amber when 2 days or fewer are left.
4. **A big button** to the exact page ("Review the handout", "Make the changes", "Allocate now"), plus the plain
   link below it. Links survive sign-in, including BITS sign-in (fixed in v1.4.2).
5. **What happened**, specific to the event (§2).
6. **Handout details:**
   - course code and title;
   - semester, with its start date;
   - programme and department;
   - HMP reference and current status (plain words);
   - version number and when it was saved;
   - Course Dibba slot and day;
   - exam date, when the semester has one.
7. **People:** Instruction Cell contact, HOG, PC, faculty (Instructor-in-Charge first, from the Dibba's lead
   instructor) and SME, with names and emails. Only the roles the request has so far. "Away until … · back-up …"
   is shown next to anyone away.
8. **Recent steps:** the last 3–5 steps with dates and names, from the same history as the request page.
9. **Footer:**
   - why you got it ("…because you are the faculty on this handout");
   - a link to My settings (instant or one email a day);
   - the help contact;
   - either "Please do not reply" or "Replies go to <IC mailbox>" (§4).

**Technically:**

- Built with tables and inline styles, so it looks the same in Outlook, Gmail and phones (screenshot 02b at phone
  width).
- Every email also has a full **plain-text** version (05b).
- Dates use India time and read like "05 Dec 2026".
- The header has a small BITS logo (14 KB, served from HMP). When the mail client blocks images, the header still
  reads "Handout Management Portal · BITS Pilani WILP".
- The bell (in-HMP notice) keeps its one-line text; only emails get the full layout.

## 3. Rules (and how they're kept)

- **Never in an email:** passwords, tokens or the handout's content. "What changed" names sections and counts,
  not text. Reviewer comments, reasons and comment text are shown in full: they are messages to the reader.
- **Each person sees only what their own request page shows them.** Everyone named on a request already sees
  the people, status and comments there, so the details and people boxes are the same for all recipients. The
  difference is the link (their own page) and the "what you need to do" (their own step).
- **Never slows a page:** emails are built and sent after the page has answered, as today. A mail-server problem
  is recorded on the email's row and never shown as an error to the person who clicked.
- **Missing data leaves no gap:** no exam date, no SME yet, no Dibba entry or first version — that line is left
  out. Tests check each case.

## 4. Admin → Notifications (rebuilt)

Text mock-up (built after approval):

```
Admin → Notifications

[ Emails ]  [ Email log ]  [ Settings ]

Emails ─────────────────────────────────────────────────────────────────────────────
Event                      To          Subject (edited ✎)                              ...
New request                HOG         Action needed: allocate {{course}} ({{semester}})   [Edit] [Preview]
Sent back for changes      Faculty     Changes needed: {{course}} ({{semester}}) ✎         [Edit] [Preview]
...

Edit "Sent back for changes — to the faculty"
  Subject        [ Changes needed: {{course}} ({{semester}})                    ]
  Summary        [ {{actor}} sent the handout for {{course}} back to you for changes. ]
  What to do     [ Read the comments below, make the changes and submit it again. ]
  Placeholders:  {{course}} {{courseCode}} {{courseTitle}} {{semester}} {{programme}} {{refNo}}
                 {{actor}} {{name}} {{dueDate}} {{daysLeft}} {{step}}
  [Save]  [Back to the original wording]

Preview with: request [ HMP-2026-0057 · SE ZG503 ▾ ]  as [ Faculty ▾ ]
  ┌ the real email, rendered ┐            [Send a test to me]
```

- **Edit the wording:** each event and audience has an editable subject, summary and "what to do", with
  placeholders listed next to the editor. **Back to the original wording** restores the built-in text. The
  layout, details, people, history and footer are fixed, so an edit can't break an email. An unknown
  `{{placeholder}}` is refused when you save.
- **Preview with a real request:** pick any request and audience. It shows exactly what would be sent, built from
  today's data.
- **Send a test to me:** the same email to your own address, subject starting "TEST". It is audit-logged.
- **Email log:** every email of the last 90 days: when, to, subject, event, request, **Sent / Failed (with the
  error) / Waiting for the digest**. Filter by failed, person, or request reference.
- **Settings:**
  - **Reply-to address** (e.g. the IC mailbox), or empty for "Please do not reply";
  - **Help contact** shown in every footer (e.g. "Instruction Cell, ic-wilp@…").
- The old "Time limits" card goes (due dates live in Admin → Workflow since v1.4.2); a link to Workflow replaces
  it.

## 5. Daily digest and bulk actions

- **Digest (screenshot 11):** the same facts, compact. Each held notice stores its compact block (title, course,
  semester, reference, status, due) when it is held, so the 09:00 email doesn't depend on later changes. "Action
  needed" comes first, soonest due first; then "For information".
- **Bulk actions (H31):** kick-off, bulk upload, bulk allocate, bulk review and bulk publish send **one email per
  person** listing every request, in the digest's compact form. Today they send one email per request. The bell
  still gets one notice per request.

## H. Decisions (approved 11 Nov 2026: all as recommended, with one change)

- **H33 change:** the welcome tick box is **on** for Add person but **off by default in the People upload**.
  When it's ticked, the upload says "Sends a welcome email to N people". Re-send stays on Edit person.
- **H28:** you enter the IC mailbox and the help wording after the release.

### As proposed

- **H28 — reply-to:** an Admin setting. Empty means "Please do not reply" (today's behaviour, but said in the
  email). Set to the IC mailbox, replies go there. _Recommended._ **I need the IC mailbox address and the help
  contact wording** (or you type them in Admin → Notifications → Settings after the release).
- **H29 — editable wording scope:** subject, summary and "what to do" per event and audience. The layout, details,
  people, history and footer stay fixed. _Recommended:_ an Admin edit can't remove the due date, the button or the
  details. Full free-form templates would be the alternative.
- **H30 — comment emails:**
  - @mentions: email at once (as now);
  - **replies to a thread you're in:** email (new);
  - plain new comments: bell only (as now; they come in the digest for digest users).
  - _Recommended._ Emailing every comment to everyone on the request would be noisy (a busy review has 10–20).
- **H31 — bulk actions send one email per person** listing the requests, instead of one per request.
  _Recommended:_ a 40-course kick-off otherwise sends a HOG 40 long emails at once.
- **H32 — email log:** the existing `Notification` rows, shown in Admin → Notifications → Email log (90 days).
  Failures and test sends are also written to the audit log. _Recommended._ Writing every email to the audit log
  too would double the rows and bury the audit log's own entries.
- **H33 — welcome emails:** sent when a person is added on Edit person, and for people added by the People upload
  (a "Send welcome emails" tick box on Apply, ticked by default). A **Send welcome email** button on Edit person
  re-sends it. People who already exist get none, unless you press that button. _Recommended._ The sign-in line
  follows the setup:
  - "Sign in with your BITS ID" when BITS sign-in is set up on the server;
  - otherwise "The administrator will give you your password".
- **H34 — the logo:** a small copy (14 KB) loaded from the HMP site. Some Outlook setups show it only after
  "Download pictures"; the header reads fine without it. _Recommended._ Embedding it in every email instead (about
  20 KB more each, always shown) is the alternative.

_Not in v1.4.3:_ emails when a due date is changed by hand. The history and My work already show it; say if you
want an email too.

## I. As built (and what I found on the way)

- **How the wording is stored.** Each email in the catalogue (`lib/email/catalogue.ts`, 38 emails) has
  built-in wording. An Admin edit is a `NotificationTemplate` row keyed `email:<email>`. The summary goes in
  `body` and "what to do" in the new `action` column. The plan's separate `summary` column turned out not to
  be needed.
  - The seed never touches these keys, so a release can improve the built-in wording without overwriting an
    edit.
  - Saving the original wording again removes the row.
- **The bell keeps its one line.** It still uses the 18 seeded templates. Only the email is new.
- **Bulk actions** collect their notices and send them as one batch (`notifyTransitions`, a new
  `transition_batch` job in the worker). People on the daily digest get the items in their digest instead.
- **Every other sender** now uses the layout:
  - hand-over, reminders and escalation;
  - back-up named, and a new "you are no longer X's back-up" when someone picks a different back-up;
  - Taxila run finished, auto-publish stopped;
  - Mode B export and manual publish;
  - the weekly summary.

  Anything still built the old way gets the layout with its sentence, so no email goes out bare.

- **Found by the tests:** emails built the old way didn't carry the reply-to and help contact in their
  footer. Fixed in `deliver()`.
- **Role-change emails** are sent from Edit person and Undo, not from a People upload, which could change many
  people at once.
- **The preview** uses example text, marked "(example)", where a request has none yet: no comment, no Taxila
  publish, or no sent-back comments.
- **Tests:**
  - `lib/email/__tests__/emails.test.ts`: 21 unit tests. Every step for every role, escaping, gaps, the
    welcome without a password, and wording edits.
  - `lib/__tests__/emails.integration.test.ts`: 5 tests on the real database. Send-back comments, back-up
    copy, one bulk email, digest blocks, and a failed send in the audit log with the reply-to.
  - `notifications-email.test.ts`: +2 tests.
  - `e2e/emails.spec.ts`: 3 tests. Edit and refusal, preview, test send and log, reply-to, and the welcome
    box ticked on Add person.
  - `people.spec.ts`: the upload box is off by default with its count line, nothing is sent while it's
    unticked, and a person added on Add person gets the welcome email.
- **Not done:** "what changed" is checked in the unit tests and through the database path, but not with two
  real structured handouts in the integration test.
